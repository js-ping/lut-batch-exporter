# 版本说明

## v1.6.0 — 2026-10-27

### 时长预估：开始前知道要多久，跑起来知道还剩多久

以前只有进度条和「剩 hh:mm」这几个字，而且是**每跑完一条才跳一次**，中间几十分钟一直是旧数字。现在拆成两件事：

**① 点开始之前就给结论**

选好文件夹、LUT、格式，底部条和运行面板立刻显示：

```
素材总长 18:40   整批预计需要 约 8 分钟（估）   待处理 40 / 跳过 3 个文件
```

「要多久」不是拍脑袋写的常数，是在这台机器上用真实命令实测标定出来的：

| 输出尺寸 | HEVC | H.264 | ProRes 422 |
|---|---|---|---|
| 3840×2160 | 0.89x | 0.93x | 0.31x |
| 1920×1080 | 3.16x | 3.47x | — |

把「速度 × 百万像素」算出来基本是常数，所以按**输出像素数**反推，而不是按「1080p / 4K」分类——裁成竖屏之后像素少了、速度变快，也能自动算进去。LUT 级数、强度混合、质量档位都会往下打折。

模型对得上实测：4K HEVC 估 0.84x（实 0.89）、1080p 估 3.38x（实 3.16）、4K ProRes 估 0.31x（实 0.31），误差 ±7% 以内。

**② 跑起来之后以实测为准**

不再等到一条跑完才更新。现在每解析一行 ffmpeg 进度就重算一次整批的时间账：

```
已处理 05:20 / 18:40    剩余 约 02:10    整批 约 07:30    速度 3.34x
```

- 剩余时长 = 还没处理的素材长度 ÷ 当前实测速度，每 0.4 秒刷新
- `speed` 偶尔是 `N/A`，就退回用「已处理媒体秒 ÷ 已流逝墙钟秒」自己算
- 每条跑完用**实际时长**校准一次，误差不累积
- 跳过 / 失败 / 拒绝的文件也计入「已处理」，否则跑完了剩余时长还挂着不为零
- 结束后显示「整批实际用时」

实测一次真跑（3 条 12 秒 1080p，HEVC）：开工估 11 秒，实际 10.8 秒；中途剩余时长 14.4 → 9.4 → 8.6 → 7.4 → 5.3 → 4.1 → 3.5 → 1.1 → 0，一路往下走，没有卡住或跳涨。

另外「要生成 40 个以上文件」的确认框里也会带上预计时长。

### LUT 用途辨别：这个 LUT 该喂 Log，还是该喂已还原的画面

`程序/lut_analyze.py`（新文件，零依赖）。核心判断依据是**曲线形状**，不是文件名：

| | Log→709 转换 LUT | 风格 LUT |
|---|---|---|
| 中性轴中段斜率 | **2.20**（实测 Apple Log→Rec.709） | 0.86 ~ 1.2（只微调） |
| 黑位 | 0.000（技术转换压到纯黑） | 常抬到 0.02~0.09（胶片味） |
| 色度倍率 | 1.3 ~ 3.3（要把扁的灰片拉开） | 0.6 ~ 1.0（反而收一点） |

Log 素材天生「扁」——一大段动态范围压在很窄的码值区里，所以还原它必须大幅拉开反差；风格 LUT 作用在已经还原好的画面上，只需微调。这就是能靠读数把它们分开的原因。

界面上：列表每行一枚徽章 `Log 用` / `709 用` / `判不准`，鼠标悬停看判定理由和实测数字；上方一排筛选按钮带实时计数：

```
全部 101 | Log 用 56 | 709 用 24 | 判不准 21
```

素材判定为灰片时，那一行提示会变成「这批素材是灰片 → 优先挑 Log 用的（56 个），其余直接套会发灰发脏」。

**用你自己的 101 个 LUT 验过**（这个库的文件夹名正好互相印证）：

| 文件夹 | 判 Log | 判 709 | 判不准 |
|---|---|---|---|
| 709电影感系列(手机用) | 0 | 7 | 3 |
| log灰片格式使用 | 5 | 0 | 1 |
| 相机用/佳能clog专用 | 8 | 0 | 1 |
| 相机用/索尼等其它log灰片电影感系列 | 8 | 0 | 1 |
| 相机用/柯达2383 | 7 | 0 | 0 |
| 青青独家调色LUT包 | 7 | 0 | 0 |

标注 709 的文件夹里一个 Log 都没误判，标注 log 的文件夹里也一个 709 都没有。判不准的（比如 `warm.cube` 斜率 1.19、黑位 0.005）保留「判不准」而不是硬猜——这种情况本来就该用试色板看一眼。

101 个 LUT 全量分析 0.7 秒（平均 6.7 ms/个），结果按「算法版本 + 文件大小 + mtime」缓存到 `程序/lut_meta.json`，第二次打开不重算。

顺带修的三处：

- **`read_cube_signature` 原来读不了真实 LUT**。Resolve 导出的 `.cube` 头和数据之间有一行空行，被当成数据行 → 整批读崩（101 个里有 84 个读不出）。现在空行、注释、`DOMAIN_MIN/MAX` 都能正确处理，并且支持「一维整形表 + 三维表」的写法。
- 自动挑转换 LUT 时，曲线判定为「709 用」的直接压下去（-9 分），不再把风格 LUT 塞进 ① 槽。
- 「这批没有转换型 LUT」的拦截提示改用曲线结论，不再只认文件名。

## v1.4.0 — 2026-10-26

### 修复：点「开始导出」毫无反应

**原因**：原生窗口用的是 `WKWebView`，它**默认不实现 `WKUIDelegate` 的 `runJavaScriptConfirmPanel`**。页面里调 `confirm()` 不会弹窗，而是**静默返回 false**。

界面上的路径正好踩中：

```js
if(!payload.luts.length && !confirm('没有选任何 LUT，…')) return;
```

没选 LUT → `confirm()` 返回 false → 直接 return → 一个字节的反馈都没有。

`程序/native/main.swift` 里原本确实没写 `uiDelegate`，所以这个问题从有原生窗口起就存在，只是**之前所有测试都走 HTTP 接口，没走界面点击**，一直没暴露。

**改法（双保险）**：

1. 前端把 3 处 `confirm()` 全部换成自绘弹窗 `askModal()` —— 不依赖浏览器 API，app 和 `启动.command` 里行为一致，还能做得更好看（支持 ESC / 回车 / 点遮罩关闭）
2. `main.swift` 补上 `WKUIDelegate`，实现 `alert` / `confirm` / `prompt` 三个原生对话框，别的 JS 弹窗也能用了

**验证**：DOM 桩跑了 5 个场景 13 项断言全过——

| 场景 | 期望 | 结果 |
|---|---|---|
| 没选 LUT 点导出 | 弹框，不静默退出 | ✅ |
| 弹框点「回去选 LUT」 | 不发起导出 | ✅ |
| 弹框点「仍然导出」 | 正常 POST 导出 | ✅ |
| 目录相同 | 先弹警告，可换目录 | ✅ |
| 槽都填了 LUT | 不弹框直接跑 | ✅ |
| 41 个文件 | 先弹数量确认 | ✅ |

### 新增：LUT 可以从列表里移除

列表每行末尾加了一个 **✕**。点一下就把这个 LUT 从列表收起来，列表标题会变成「显示 26 / 27」，旁边出现橙色 **「已隐藏 1 · 恢复」**，点一下全部放回来。

几个设计上的取舍：

- **不删文件**。做的是「收起」不是「删除」，磁盘上的 `.cube` 原封不动。误删素材是没法挽回的，误「收起」点一下就好了
- 如果被收起的 LUT 正挂在 ① 或 ② 槽里，**顺手清空那个槽** —— 否则会出现「列表里看不见它，但导出时它还在生效」这种最难受的状态
- 记录存在 `程序/lut_hidden.json`，删掉这个文件 = 全部恢复
- 想真的删文件：用「在访达中打开」自己删，工具永远不碰你的原始文件

- 版本号、说明书、目录说明同步

## v1.3.0 — 2026-10-26

两个诉求：**按停止要能立刻停**、**没有转换 LUT 也能把灰片还原**。

### 修复：停止按钮「按了很难停」

**原因**：停止标志只在「任务循环开头」检查，`exec_ffmpeg` 内部完全不看它。所以按下去之后，当前这条素材会一直跑到结束才停。一条 4K 素材套两条 LUT 约 0.5 倍实时，1 分钟的片子就要干等 2 分钟。

**改法**：

- `exec_ffmpeg` 里加了个看门狗线程，每 150ms 检查一次停止标志，一旦置位立刻 `SIGTERM`，1.2 秒不退出就 `SIGKILL`
- `/api/stop` 除了置标志，还主动掐一次（看门狗是兜底，这个才是主路径）
- **停止后删掉半成品文件**。这一步是关键：不删的话，下次开「跳过已导出」会把这个坏文件当成已完成而跳过，白跑一遍还拿不到东西
- 停止不再记为「失败」，单独统计「已停止 N 项」，界面上用暗红色 chip 显示
- 按钮点击后立刻变「正在停止…」并锁住，避免连点

**实测**（1080p / 90 秒素材，ProRes 422 HQ 输出）：

| 指标 | 结果 |
|---|---|
| 停止耗时 | **0.43 秒**（原来要等整条跑完，约 300 秒） |
| ffmpeg 残留进程 | 无 |
| 半成品残留 | 0 个 |
| 已完成的文件 | 完整保留 |
| 停止后立刻重新开始 | 正常，3 条全跑完 |

### 新增：「仅色彩还原」——不用 .cube 文件也能还原灰片

问题背景：网上买的「万能 LUT 包」全是风格 LUT，没有转换 LUT，用户手上就是这种情况——27 个 LUT 全是风格型的，一条灰片都出不了正常色。

做法：按 Apple 白皮书公开的常量，**用数学算出转换曲线**，内置成 `.cube`，一键挂到 ① 槽。

| 项目 | 内容 |
|---|---|
| 曲线常量 | `R0=-0.05641088`、`Rt=0.01`、`c=47.28711236`、`β=0.00964052`、`γ=0.08550479`、`δ=0.69336945` |
| 校验 ① | `encode(0.18) = 0.4882725`，对应白皮书「18% 灰落在 10bit 500」 |
| 校验 ② | `decode(1.0) = 12.00`，对应白皮书「clip at 1200% scene reflection」 |
| 校验 ③ | 编码/解码往返误差 4.4e-16 |
| Apple Log 2 色域 | Apple Wide Gamut R(0.725,0.301) G(0.221,0.814) B(0.068,−0.076)，D65 |
| Apple Log 色域 | Rec.2020 R(0.708,0.292) G(0.170,0.797) B(0.131,0.046)，D65 |
| 输出 | Rec.709 原色 + BT.709 分段 OETF，33³ 网格，各约 950 KB |

**关键发现**：查资料时确认了一件反直觉的事——**Apple Log 和 Apple Log 2 的 gamma 曲线完全相同**，区别只在色域（Rec.2020 → Apple Wide Gamut）。两个独立来源互相印证，且 Apple Log 2 白皮书（2025-09）沿用同一组编码常量。所以两者共用一条曲线，只需要两套色域矩阵。这也解释了为什么错配的转换 LUT 表现为「曝光对、高饱和颜色怪」。

**实测**（真实 iPhone 17 Pro Max 素材，竖屏 3840×2160 60fps，傍晚操场）：

| 指标 | 原始灰片 | 套内置 Log 2 曲线 |
|---|---|---|
| 黑位 YLOW | 82 | 46 |
| 高光 YHIGH | 181 | 235 |
| 平均亮度 | 126.9 | 132.5 |
| 饱和度均值 | 3.8 | 7.5 |

视觉验证：天空从死灰变成有金色渐变、跑道恢复砖红、草地恢复绿色、白栏杆真正变白，无偏绿/偏品红。饱和度均值低是因为画面 70% 是天空和灰白建筑，彩色像素占比小。

**界面**：

- Log 识别框里加「仅色彩还原」按钮（橙色强调），与原来的「从我的库里挑转换 LUT」并排
- 点击后：① 槽填内置曲线、② 槽清空（所以才叫「仅」），按钮变成 `✓ 仅色彩还原`
- 槽位显示「内置 · Log 2 还原」而不是文件名，并用橙色标出，一眼能区分是内置还是自己的 LUT
- 提示条说明当前状态；如果 ② 槽又挂了风格 LUT，会提醒「那就不是『仅』还原了」
- 下拉切换 Apple Log / Apple Log 2 时，内置曲线跟着换对应版本
- 橙色拦截条的文案改了：以前只会说「需要单独准备一个转换 LUT」，现在会说「不用另外找文件，点『仅色彩还原』就行」

**已知取舍**：内置版本对高光按 Rec.709 上限直接截断，不做柔和滚降（这样最可预期，也不会让画面发灰）。正规转换 LUT 有时会在高光做 rolloff，所以极亮天空的过渡会稍「硬」一点，可以用画面微调压 0.2–0.3 EV 补。

## v1.2.0 — 2026-10-26

这一版是照着「全网同类工具（DaVinci Resolve 的 Log 识别、Hedge/ShotPut Pro 的转码队列、Blackmagic 官方 LUT 流程、ffmpeg 生态的 lut3d 实践）」逐项对照后补齐的。核心思路只有一条：**灰片调色最容易错在第一步——把风格 LUT 直接套在 Log 上**。所以这一版把「先认清素材是什么」做成了流程的起点。

### 新增

**1. 素材色彩曲线自动识别 + 手动覆盖**

- 打开素材目录即逐条判定：Apple Log 2 / Apple Log（1 代）/ 其它 Log 曲线 / Rec.709 已转换
- 两级判据：先看元数据标签（`AppleLog2`、`arib-std-b67`、`smpte2084`、`bt709` 等，命中即高可信）；元数据没有时抽单帧看像素特征（灰度片饱和度极低）
- **明确承认能力边界**：Apple Log 1 与 Log 2 的像素特征几乎一样，无法从画面数据区分。所以判定框旁边给一个下拉，可以手动指定
- 顶部汇总这批素材的构成；一批里混了几种曲线会直接标「素材类型不一致」，提示分开处理
- 识别完点「按识别结果自动挑转换 LUT」，从 LUT 库里按名字打分匹配（`AppleLog2` > `AppleLog` > `Rec709`），不用自己翻目录

**2. 灰片未挂转换 LUT 的强制拦截**

- 素材是灰片但转换槽空着 → 顶部亮橙条警告，不允许稀里糊涂直接导出
- 更进一步：会检查 LUT 库里**是否存在转换型 LUT**。如果没有，直接说明「网上买的『万能 LUT 包』几乎全是风格 LUT，需要单独准备转换 LUT」——这是实测里最高频的踩坑点

**3. LUT 库管理**

- 收藏（★），存 `程序/lut_fav.json`，跨会话保留
- 「只看收藏」一键过滤；「最近用过」保留 12 条，切换项目不用重新翻
- 显示每条 LUT 的来源子文件夹（LUT 包里同名文件很多，光看文件名分不清）
- 搜索同时匹配文件名和目录名

**4. 多画幅一次输出**

- 5 种比例可多选：原画幅 / 16:9 横屏 / 9:16 竖屏 / 1:1 方形 / 4:5 竖幅
- 素材只解码一遍，同时产出多个比例，不用重复跑
- 中心裁切，Python 端算好偶数矩形（避免滤镜表达式里的逗号转义地狱），宽高强制偶数（HEVC 要求）
- 素材本身已是目标比例时自动跳过，不白生成一份副本
- 说明书里写清了「中心裁切对构图有要求，竖屏输出可能把人裁掉」

**5. 音频四模式**

| 模式 | 行为 |
|---|---|
| 保留原音 | 能拷贝就拷贝；PCM 进 mp4 时自动转 AAC 256k |
| 静音 | `-an`，彻底去掉音轨 |
| 合并单声道 | `-ac 1` + AAC 128k |
| 响度标准化 | `loudnorm=I=-16:TP=-1.5:LRA=11` + AAC 192k |

无音频源的素材不会误接 `loudnorm`（会报 `Stream specifier ':a' matches no streams`），单独走无音频分支。

**6. 画面微调（在 LUT 之后生效）**

- 曝光 `-3.0 ~ +3.0 EV`（乘性，接近真实曝光，不动黑位）
- 对比度 `0.50 ~ 1.50`
- 饱和度 `0.00 ~ 2.00`
- 色温 `-100 ~ +100`（正数偏暖 / 负数偏冷）

四项都实测确认生效（`sample_stats` 前后对比）：饱和度 +30% → 50→65；对比度 +20% → 动态范围 71→85；曝光 +0.5EV → 平均亮度 145→187。色温方向做过实测校正——`colortemperature` 滤镜是 K 值越低画面越暖，所以界面上的「暖」映射成 `6500 - temp*25`。

**7. 导出报告**

- 每次批处理自动在输出目录写 `_导出报告_YYYYmmdd_HHMMSS.csv`
- 13 列：源文件、输出文件、画幅、时长、分辨率、编码、码率、音频、色彩曲线判定、转换 LUT、风格 LUT、强度、状态
- UTF-8 带 BOM，Excel 双击不乱码
- 导出完在界面上一键「在访达中显示报告」

**8. 逐条体检与预检拦截**

- 素材列表每行带判定徽章（`Log 2` / `Log` / `Rec709` / `8bit` / `无音轨`）
- 8bit 素材 → 黄色提醒；读不到分辨率 → 直接拒绝；yuvj 全范围 → 提醒
- 底部状态栏实时算「素材 N 条 · 输出 M 个文件 · 预计 X」

### 修复

- **判定徽章完全不显示**：`.fb{}` 那组 CSS 规则在 WKWebView 里被整组忽略（徽章塌成 0 尺寸）。查了很久，先怀疑数据缺失、再怀疑被裁切，最后用红框 `!important` 测试确认是样式规则本身失效。改用内联样式生成后正常
- **徽章被挤到下一行看不见**：`display:grid` 容器里 HTML 模板的多行空白文本节点会变成多余网格单元，把第 4 个元素推到第二行。改用 `display:flex` + `cells.join('')` 消除字面空白
- **Log 判定汇总逻辑错**：2 条素材（1 条 Log + 1 条正常）被强行归为「其它 Log 曲线」，理由是「多数素材属于这一类」——而 1 条根本不算多数。改为占比 ≥60% 才采信，否则标「素材类型不一致」
- **像素推断判据不可靠**：原来同时看饱和度和黑位，但测试图案本身不黑，黑位基线（YLOW=41）让正常片被判成「无法判定」。改为纯饱和度阈值：<30 判 Log、<38 判偏向 Log、≥38 判 Rec.709。另外必须先 `format=yuv420p` 归一化，否则 10bit 素材 YAVG 500+ 无法设阈值
- **探针重复调用拖慢扫描**：同一目录反复扫描每次都重新 `ffprobe`。加两级缓存（`运行记录/.cache/probe_cache.json`、`detect_cache.json`），按 `path|mtime|size` 命中，超 4000 条自动裁剪到最近 2000

### 自检

自检从 25 项扩到 **52 项全绿**，新增 6 个 section：Log 曲线识别、音轨四模式、多画幅裁切、画面微调、导出报告、扫描与命名。

## v1.0.0 — 2026-10-25

首个可用版本。

**功能**

- 批量把 Blackmagic Camera 拍的 Apple Log 2 灰片套 LUT 导出
- 两级 LUT 串联：转换 LUT（Log→Rec.709）+ 风格 LUT（创作风格）
- 四种输出：ProRes 422 HQ / ProRes 422 / HEVC 10bit / H.264 8bit
- LUT 强度可调（0–100%，只作用于最后一个 LUT，用 blend 混合实现）
- 输入色域矩阵可强制指定（自动 / BT.2020 / BT.709）
- 试色板：抽单帧，把多个 LUT 各渲一张排成网格对比
- 断点续跑：跳过已导出的文件
- 导出强制写入 `bt709` 色彩标签，规避「导出后偏色发暗」
- 保留子目录结构；音轨能拷贝就拷贝，PCM 进 mp4 时自动转 AAC
- 停止按钮在当前文件跑完后安全停下，不留半成品

**实测（MacBook Air M3，8 核，macOS 15.8）**

| 素材 | 输出 | 速度 |
|---|---|---|
| 4K 30p | HEVC 10bit 40M | 0.51× 实时 |
| 4K 30p | ProRes 422 | 0.29× 实时 |
| 1080p 30p | HEVC 10bit | 1.77× 实时 |

**修掉的问题（开发过程记录）**

- `lut3d` 的路径参数名在 ffmpeg 各版本不同（`file` vs `filename`），改为启动时自动探测
- `-map` 只映射视频导致音轨全部丢失 → 补 `-map 0:a?`
- 前端用 GET 读设置但后端只实现 POST → 补 GET 路由，自动恢复设置才生效
- 试色板临时图堆积 → 启动时只保留最近 3 次

**已知限制**

- 三维 LUT 是纯 CPU 逐像素运算，4K 素材约 0.3–0.5× 实时，无法再快（ffmpeg 无 GPU LUT 加速）
- 只支持 `.cube` / `.3dl` / `.dat` / `.m3d` / `.csp` 三维 LUT，不支持 Adobe `.look`、`.xmp`
- 单进程串行处理，实测多开进程无提速（单进程已吃满 CPU）
- 不做自动白平衡 / 曝光校正，这些要在拍摄时或剪辑时解决
